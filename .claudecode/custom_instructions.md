# Claude Code Git/GitHub ワークフロー自動化スキル指示書

## 🎯 目的
このプロジェクトにおけるコード変更、テスト、コミット、およびプルリクエスト（PR）の作成を、指定された手順に沿って安全かつ一貫した品質で自動実行する。

## 🛠️ 事前条件
- 開発者は事前に `gh auth login` を済ませていること。
- コマンド実行前に必ず変更内容の差分を確認すること。

## 📋 ワークフロー手順

### 1. コード検証 (Verify)
変更が完了したら、コミット前に必ず以下のコマンドを実行して品質を検証する。
- リンター・フォーマッタの実行: `npm run lint` または `npm run format`
- テストの実行: `npm run test`
※ プロジェクトの構成（Python, Go等）に応じて適切なテストコマンドに読み替えること。テストが失敗した場合は、そこで処理を中断しユーザーに修正方針を確認する。

### 2. ブランチ作成
タスクに応じた適切なブランチを作成し、切り替える。
- 命名規則: `feature/内容`, `bugfix/内容`, `docs/内容`（例: `feature/auth-login`）
- コマンド: `git checkout -b <branch-name>`

### 3. コマンドラインでのコミット
変更内容をステージングし、**Conventional Commits** 規約に準拠したメッセージでコミットする。
- コミット前に必ずユーザーに確認する（`git status`/`git diff` の内容を示した上で）。ユーザーの明示的な許可なく勝手にコミットしない（`gh-pr-creator` スキルと同じ方針）。
- ステージングは変更したファイルを明示的に指定する（`git add .` や `git add -A` のような一括addは、意図しないファイル（.env、認証情報など）を巻き込む恐れがあるため避ける）。
- 命名規則: `<type>(<scope>): <description>`
  - `feat`: 新機能
  - `fix`: バグ修正
  - `docs`: ドキュメントのみの変更
  - `style`: コードの意味に影響を与えない変更（空白、フォーマットなど）
  - `refactor`: バグ修正や新機能追加ではないコードの変更
- コマンド例: `git add <対象ファイル...>` および `git commit -m "feat(auth): ログイン機能の実装"`

### 4. プルリクエスト (PR) の作成
ブランチをリモートにプッシュし、GitHub CLI (`gh`) を使用してPRを作成する。
- プッシュ: `git push origin HEAD`
- PR作成: `gh pr create --title "<コミットメッセージと同等のタイトル>" --body "<変更内容、テスト結果、影響範囲の要約>"`
- 作成完了後、発行されたPRのURLをユーザーに提示する。

## ⚠️ 禁止事項と注意点
- ユーザーの明示的な許可なく `git push origin main`（または `master`）への直接プッシュは絶対に行わない。
- ユーザーの明示的な許可なくコミットしない（3.を参照）。
- テストが失敗している状態でのコミット・PR作成は禁止する。プロジェクトにテストコマンドが存在し実行可能な場合は、コミット前に実行し結果を確認する。テストコマンドが存在しない、または今回の変更に対して意味を持たない場合は、無理に実行せず、PR本文の動作確認欄に「未確認」である旨を正直に明記する（`gh-pr-creator` スキルの方針に合わせる）。
