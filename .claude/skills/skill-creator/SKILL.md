# Skill Creator

新しいスキルを作成し、反復的に改善していくためのスキルです。

スキル作成のプロセスは大まかに以下のようになります：

*   スキルに何をさせたいのか、そして大まかにどのように実行させるかを決定します。
*   スキルのドラフトを作成します。
*   いくつかのテストプロンプトを作成し、そのスキルにアクセスできる状態のClaudeを使用してプロンプトを実行します。
*   定性的および定量的の両面から、ユーザーが結果を評価するのを支援します。
    *   バックグラウンドでテストを実行している間に、定量的な評価がまだない場合はいくつかドラフトを作成します（すでに存在する場合は、そのまま使用するか、変更が必要と感じた場合は修正できます）。その後、それらをユーザーに説明します（すでに存在していた場合は、既存のものを説明します）。
    *   `eval-viewer/generate_review.py` スクリプトを使用して、ユーザーが確認できるように結果を表示し、また定量的な指標も確認できるようにします。
*   ユーザーによる結果の評価フィードバックに基づいて（また、定量的なベンチマークから明らかな欠陥が判明した場合も）、スキルを書き直します。
*   満足のいく結果が得られるまで繰り返します。
*   テストセットを拡大し、より大きな規模で再度試します。

このスキルを使用する際のあなたの仕事は、ユーザーがこのプロセスのどの段階にいるかを把握し、その段階に参加して彼らがプロセスを進めるのを助けることです。例えば、ユーザーが「Xのためのスキルを作りたい」と言ったとします。あなたは、彼らが意図していることを絞り込み、ドラフトを書き、テストケースを作成し、どのように評価したいかを考え、すべてのプロンプトを実行し、そして繰り返すのを手伝うことができます。

一方で、ユーザーがすでにスキルのドラフトを持っている場合もあります。この場合、ループの「評価/反復」の部分に直接進むことができます。

もちろん、常に柔軟であるべきです。ユーザーが「たくさんの評価を実行する必要はない、ただフィーリングを合わせてくれ」と言った場合は、代わりにそうすることもできます。

そしてスキルが完成した後（ただし、これも順序は柔軟です）、全く別のスクリプトとして用意されているスキル説明改善ツールを実行して、スキルのトリガーを最適化することもできます。

いいですね？ 了解です。

## ユーザーとのコミュニケーション

スキルクリエーターは、コーディングの専門用語に対する理解度が大きく異なる幅広い人々によって使用される可能性があります。もし聞いたことがないなら（そして、どうやって聞けるというのでしょう、これが始まったのはごく最近のことです）、Claudeの力がインスピレーションとなり、配管工がターミナルを開き、親や祖父母が「npmのインストール方法」をグーグルで検索するようなトレンドが今起きています。一方で、大半のユーザーはおそらくかなりコンピューターに詳しいでしょう。

ですので、コミュニケーションの言葉遣いをどうすべきか理解するために、文脈の手がかりに注意を払ってください！ デフォルトのケースとして、いくつか例を挙げます：

*   「evaluation（評価）」や「benchmark（ベンチマーク）」は境界線上の言葉ですが、許容範囲です。
*   「JSON」や「assertion（アサーション/検証）」については、ユーザーがそれらの意味を知っているという確かな手がかりを確認してから、説明なしで使用するようにしてください。

疑問がある場合は用語を簡潔に説明しても構いませんし、ユーザーが理解できるか不確かな場合は、短い定義を添えて用語を明確にして構いません。

## スキルの作成

### 意図の把握

まず、ユーザーの意図を理解することから始めます。現在の会話には、すでにユーザーが捉えたいワークフロー（例：「これをスキルに変えて」と言うなど）が含まれているかもしれません。その場合は、使用されたツール、手順の順序、ユーザーが行った修正、観察された入力/出力フォーマットなど、まずは会話履歴から答えを抽出してください。ユーザーにギャップを埋めてもらう必要がある場合もあり、次のステップに進む前に確認を取るべきです。

1.  このスキルは、Claudeに何をできるようにすべきですか？
2.  このスキルはいつトリガーされるべきですか？（どのようなユーザーのフレーズ/コンテキストで）
3.  期待される出力フォーマットは何ですか？
4.  スキルが機能するかを検証するためのテストケースを設定すべきですか？ 客観的に検証可能な出力（ファイルの変換、データ抽出、コード生成、固定のワークフローステップ）を持つスキルは、テストケースが役立ちます。主観的な出力（文章のスタイル、アート）を持つスキルは、多くの場合必要ありません。スキルの種類に基づいて適切なデフォルトを提案しますが、決定はユーザーに委ねてください。

### インタビューとリサーチ

エッジケース、入力/出力フォーマット、サンプルファイル、成功基準、依存関係について積極的に質問してください。この部分が明確になるまで、テストプロンプトの作成は待ってください。

利用可能なMCPを確認します - リサーチ（ドキュメントの検索、類似スキルの発見、ベストプラクティスの調査）に役立つ場合は、サブエージェントが利用可能であれば並行してリサーチを行い、そうでない場合はインラインでリサーチを行います。ユーザーの負担を減らすために、コンテキストを準備した状態で臨んでください。

### SKILL.mdの作成

ユーザーへのインタビューに基づき、以下のコンポーネントを記入します：

*   **name**: スキル識別子
*   **description**: いつトリガーするか、何をするか。これは主要なトリガーメカニズムです - スキルが何をするのかと、いつそれを使用すべきかの具体的なコンテキストの両方を含めてください。「いつ使用するか」の情報はすべてここに記述し、本文には記述しません。注意: 現在、Claudeにはスキルを「過少トリガー」する傾向があります -- 役立つ場面でもスキルを使用しない傾向です。これに対抗するため、スキルの説明は少し「押し付けがましい」くらいにしてください。例えば、「社内のAnthropicデータを表示するためのシンプルで高速なダッシュボードを構築する方法。」の代わりに、「社内のAnthropicデータを表示するためのシンプルで高速なダッシュボードを構築する方法。ユーザーがダッシュボード、データ視覚化、社内指標について言及した場合、またはユーザーが明示的に『ダッシュボード』を求めていなくても、何らかの企業データを表示したい場合は、必ずこのスキルを使用すること。」のように書くかもしれません。
*   **compatibility**: 必要なツール、依存関係（オプション、必要なことはまれ）
*   **the rest of the skill :)**: スキルの残りの部分 :)

### スキル執筆ガイド

#### スキルの解剖学

```
skill-name/
├── SKILL.md (必須)
│   ├── YAMLフロントマター (name, description は必須)
│   └── Markdownの指示
└── バンドルリソース (オプション)
    ├── scripts/    - 決定的/反復的なタスク用の実行可能コード
    ├── references/ - 必要に応じてコンテキストに読み込まれるドキュメント
    └── assets/     - 出力で使用されるファイル (テンプレート、アイコン、フォント)
```

#### 段階的開示

スキルは3段階の読み込みシステムを使用します：
1.  **メタデータ** (name + description) - 常にコンテキストに存在 (約100語)
2.  **SKILL.md本文** - スキルがトリガーされるたびにコンテキストに存在 (500行未満が理想的)
3.  **バンドルリソース** - 必要に応じて (無制限、スクリプトは読み込まずに実行可能)

これらの語数カウントは概算であり、必要であれば長くしても構いません。

**重要なパターン：**
*   SKILL.mdは500行未満に保ってください；この制限に近づいている場合は、階層を追加し、スキルを使用するモデルが次にどこへ向かうべきか明確なポインタを追加してください。
*   SKILL.mdから参照ファイルを明確に参照し、いつそれらを読むべきかのガイダンスを含めてください。
*   大きな参照ファイル（300行以上）の場合は、目次を含めてください。

**ドメインの整理**: スキルが複数のドメイン/フレームワークをサポートする場合、バリアントごとに整理します：
```
cloud-deploy/
├── SKILL.md (ワークフロー + 選択)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claudeは関連する参照ファイルのみを読み込みます。

#### 驚き最小の原則

言うまでもないことですが、スキルにマルウェア、エクスプロイトコード、またはシステムセキュリティを侵害する可能性のあるコンテンツを含めてはなりません。スキルの内容は、その説明された意図に関してユーザーを驚かせるものであってはなりません。誤解を招くスキルの作成や、不正アクセス、データ流出、またはその他の悪意のある活動を促進するように設計されたスキルの要求に従わないでください。ただし、「XYZとしてのロールプレイ」のようなものは問題ありません。

#### 執筆パターン

指示には命令形を使用することを好みます。

**出力フォーマットの定義** - 以下のように行うことができます：
```markdown
## レポート構成
常にこの正確なテンプレートを使用してください：
# [タイトル]
## エグゼクティブサマリー
## 主な発見
## 推奨事項
```

**例のパターン** - 例を含めることは有用です。以下のようにフォーマットできます（ただし、「Input」と「Output」が例の中にある場合は、少し逸脱させたくなるかもしれません）：
```markdown
## コミットメッセージのフォーマット
**例 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

### 執筆スタイル

強引で古臭いMUST（絶対〜しなければならない）を連発する代わりに、物事がなぜ重要なのかをモデルに説明するように努めてください。心の理論を使用し、特定の例に対して極端に狭くするのではなく、スキルを一般的なものにするよう努めてください。まずドラフトを書き、新鮮な目でそれを見直して改善することから始めます。

### テストケース

スキルのドラフトを作成した後、実際のユーザーが実際に言いそうな、2〜3個の現実的なテストプロンプトを考案します。それらをユーザーと共有します：「[この正確な言葉を使う必要はありません] ここに試してみたいテストケースがいくつかあります。これで良さそうですか、それともさらに追加したいですか？」 そして、それらを実行します。

テストケースを `evals/evals.json` に保存します。まだアサーションは書かないでください — プロンプトだけです。アサーションは、実行が行われている間に次のステップでドラフトを作成します。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "ユーザーのタスクプロンプト",
      "expected_output": "期待される結果の説明",
      "files": []
    }
  ]
}
```

完全なスキーマ（後で追加する `assertions` フィールドを含む）については `references/schemas.md` を参照してください。

## テストケースの実行と評価

このセクションは1つの連続したシーケンスです — 途中で止めないでください。`/skill-test` やその他のテスト用スキルは絶対に使用しないでください。

結果はスキルディレクトリの兄弟層として `<skill-name>-workspace/` に置きます。ワークスペース内では、反復ごとに（`iteration-1/`、`iteration-2/` など）結果を整理し、その中で各テストケースにディレクトリ（`eval-0/`、`eval-1/` など）を割り当てます。これらをすべて前もって作成しないでください — 進行に合わせてディレクトリを作成するだけです。

### ステップ 1: 同じターンですべての実行（スキルあり と ベースライン）をスポーンする

各テストケースについて、同じターンに2つのサブエージェントをスポーンします — 1つはスキルあり、もう1つはスキルなしです。これは重要です：スキルありの実行を先にスポーンして、後でベースラインのために戻ってくるようなことはしないでください。すべてがほぼ同じ時間に終わるように、すべてを一度に起動します。

**スキルありの実行:**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**ベースラインの実行**（同じプロンプトですが、ベースラインはコンテキストに依存します）: 重要な注意点として、ベースラインのサブエージェントに「スキルパスなし」と伝えるだけでは不十分です — スキルがすでに `.claude/skills/<name>/SKILL.md` として存在している場合、そのサブエージェントの `available_skills` には引き続き表示され、参照されてしまう可能性があります。ベースラインの実行をスポーンする前に、対象のスキルディレクトリを一時的に `.claude/skills/` の外（例: `<workspace>/skill-snapshot/` へ `mv`、既存スキル改善の場合は下記のスナップショットと同じ場所でよい）へ退避させ、スキルありとベースライン両方の実行が完了してから元の場所へ戻してください。
*   **新しいスキルの作成**: スキルは全くありません。同じプロンプト、スキルパスなし、`without_skill/outputs/` に保存します。
*   **既存のスキルの改善**: 古いバージョン。編集する前に、スキルのスナップショットを取得し（`cp -r <skill-path> <workspace>/skill-snapshot/`）、ベースラインのサブエージェントをそのスナップショットに向けます。`old_skill/outputs/` に保存します。

各テストケースに対して `eval_metadata.json` を作成します（アサーションは今のところ空で構いません）。単なる「eval-0」ではなく、テスト内容に基づいた説明的な名前を各評価に付けます。ディレクトリ名にもこの名前を使用します。この反復で新しいプロンプトや変更されたプロンプトを使用する場合は、新しい評価ディレクトリごとにこれらのファイルを作成します — 以前の反復から引き継がれると想定しないでください。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "ユーザーのタスクプロンプト",
  "assertions": []
}
```

### ステップ 2: 実行中に、アサーションのドラフトを作成する

実行が終わるのをただ待つのではなく — この時間を生産的に使うことができます。各テストケースの定量的なアサーションのドラフトを作成し、ユーザーに説明します。`evals/evals.json` にすでにアサーションが存在する場合は、それらを見直し、何をチェックしているのかを説明します。

優れたアサーションは客観的に検証可能であり、説明的な名前を持っています — ベンチマークビューアで結果を一瞥した人が、それぞれが何をチェックしているのかをすぐに理解できるように、明確に読めるものであるべきです。主観的なスキル（文章スタイル、デザインの質）は定性的に評価する方が適しています — 人間の判断が必要なものにアサーションを強制しないでください。

ドラフトが完成したら、`eval_metadata.json` ファイルと `evals/evals.json` をアサーションで更新します。また、ユーザーがビューアで何を目にするか — 定性的な出力と定量的なベンチマークの両方について説明してください。

### ステップ 3: 実行が完了したら、タイミングデータを取得する

各サブエージェントタスクが完了すると、`total_tokens` と `duration_ms` を含む通知を受け取ります。このデータを直ちに実行ディレクトリの `timing.json` に保存します：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

このデータを取得できるのはこの機会だけです — タスクの通知を通じて届き、他の場所には保存されません。バッチ処理しようとするのではなく、通知が届くたびに処理してください。

### ステップ 4: 採点、集計、そしてビューアの起動

すべての実行が完了したら:

1.  **各実行の採点** — グレーダーサブエージェントをスポーンし（またはインラインで採点）、`agents/grader.md` を読み込ませて、出力に対して各アサーションを評価します。結果を各実行ディレクトリの `grading.json` に保存します。grading.json の expectations 配列は、`text`、`passed`、`evidence` というフィールドを使用する必要があります（`name`/`met`/`details` やその他のバリアントではありません） — ビューアはこれらの正確なフィールド名に依存しています。プログラムでチェック可能なアサーションについては、目視で確認するのではなくスクリプトを書いて実行してください — スクリプトの方が速く、信頼性が高く、反復間で再利用できます。
2.  **ベンチマークへの集計** — skill-creator ディレクトリから集計スクリプトを実行します：
    ```bash
    python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
    ```
    これにより、各構成の pass_rate、time、tokens が平均±標準偏差およびデルタと共に記載された `benchmark.json` と `benchmark.md` が生成されます。benchmark.json を手動で生成する場合は、ビューアが期待する正確なスキーマについて `references/schemas.md` を参照してください。各 with_skill バージョンを、対応するベースラインの前に配置します。
3.  **アナリストパスの実行** — ベンチマークデータを読み取り、集計統計が隠してしまう可能性のあるパターンを表面化させます。探すべきものについては `agents/analyzer.md` （「ベンチマーク結果の分析」セクション）を参照してください — スキルに関係なく常に合格するアサーション（識別力がない）、分散の高い評価（不安定な可能性）、時間/トークンのトレードオフなどです。
4.  **ビューアの起動** (定性的な出力と定量的なデータの両方で):
    ```bash
    nohup python <skill-creator-path>/eval-viewer/generate_review.py \
      <workspace>/iteration-N \
      --skill-name "my-skill" \
      --benchmark <workspace>/iteration-N/benchmark.json \
      > /dev/null 2>&1 &
    VIEWER_PID=$!
    ```
    反復2以降の場合は、`--previous-workspace <workspace>/iteration-<N-1>` も渡します。
    **Cowork / ヘッドレス環境:** `webbrowser.open()` が利用できない場合や、環境にディスプレイがない場合は、サーバーを起動する代わりに `--static <output_path>` を使用してスタンドアロンのHTMLファイルを書き出します。フィードバックは、ユーザーが「Submit All Reviews」をクリックしたときに `feedback.json` ファイルとしてダウンロードされます。ダウンロード後、次の反復で拾い上げられるように、`feedback.json` をワークスペースディレクトリにコピーします。
    注意: ビューアの作成には generate_review.py を使用してください；カスタムHTMLを書く必要はありません。
5.  **ユーザーに伝える**: 「結果をブラウザで開きました。2つのタブがあります — 『Outputs』では各テストケースをクリックしてフィードバックを残すことができ、『Benchmark』では定量的な比較を表示します。終わったら、ここに戻ってきて教えてください」といった内容を伝えます。

### ユーザーがビューアで見るもの

「Outputs」タブには、一度に1つのテストケースが表示されます：
*   **Prompt**: 与えられたタスク
*   **Output**: スキルが生成したファイル。可能な場合はインラインでレンダリングされます。
*   **Previous Output** (反復2以降): 前回の反復の出力を示す折りたたみセクション
*   **Formal Grades** (採点が実行された場合): アサーションの合否を示す折りたたみセクション
*   **Feedback**: 入力中に自動保存されるテキストボックス
*   **Previous Feedback** (反復2以降): テキストボックスの下に表示される、前回のユーザーのコメント

「Benchmark」タブには統計の要約が表示されます：各構成の合格率、タイミング、トークン使用量、評価ごとの内訳、アナリストの観察結果などです。

ナビゲーションは「前へ/次へ」ボタンまたは矢印キーで行います。完了すると、「Submit All Reviews」をクリックして、すべてのフィードバックを `feedback.json` に保存します。

### ステップ 5: フィードバックを読む

ユーザーが完了したと伝えてきたら、`feedback.json` を読みます：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "チャートの軸ラベルがありません", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "完璧、素晴らしい", "timestamp": "..."}
  ],
  "status": "complete"
}
```

フィードバックが空の場合は、ユーザーが問題ないと考えたことを意味します。ユーザーが具体的な不満を持っていたテストケースの改善に注力してください。

使用が終了したら、ビューアサーバーを終了します：

```bash
kill $VIEWER_PID 2>/dev/null
```

## スキルの改善

これがループの核心です。テストケースを実行し、ユーザーが結果をレビューしたので、今度は彼らのフィードバックに基づいてスキルをより良くする必要があります。

### 改善についての考え方

1.  **フィードバックから一般化する。** ここで起こっている大きな構図は、多くの異なるプロンプトにわたって数百万回（文字通りかもしれませんし、もっと多いかもしれません）使用できるスキルを作成しようとしているということです。ここでは、速く進めるために、あなたとユーザーは少数の例だけで何度も反復しています。ユーザーはこれらの例を熟知しており、新しい出力を素早く評価できます。しかし、あなたとユーザーが共同開発しているスキルが、それらの例でしか機能しないのであれば、それは無用です。細かすぎる過剰適合の変更や、抑圧的で窮屈な「MUST（絶対〜）」を詰め込むよりも、もし頑固な問題があるなら、視野を広げて異なるメタファーを使用したり、異なる作業パターンを推奨したりしてみてください。試すのは比較的低コストであり、何か素晴らしいものにたどり着くかもしれません。
2.  **プロンプトを無駄なく保つ。** 役割を果たしていないものは削除します。最終的な出力だけでなく、トランスクリプトを必ず読んでください — もしスキルが、非生産的なことにモデルに多くの時間を浪費させているように見える場合は、そうさせているスキルの部分を取り除き、何が起こるか見てみることができます。
3.  **「なぜ」を説明する。** 強引な古い MUST を使う代わりに、なぜそれが重要なのかをモデルに説明するように懸命に努力してください。今日のLLMは*賢い*です。彼らは優れた心の理論を持っており、適切なハーネス（手綱）を与えられれば、機械的な指示を超えて物事を実際に起こすことができます。ユーザーからのフィードバックが素っ気ないものであったり、イライラしているものであったとしても、タスクやユーザーがそれを書いた理由、実際に何を書いたかを理解しようと努め、その理解を指示に変換してください。もしすべて大文字で ALWAYS や NEVER と書いたり、超厳格な構造を使用していることに気付いたなら、それは黄色信号です — 可能であれば、あなたが求めていることがなぜ重要なのかモデルが理解できるように、理由を再構成して説明してください。それが、より人間的で、強力で、効果的なアプローチです。
4.  **テストケース間で繰り返される作業を探す。** テスト実行のトランスクリプトを読み、サブエージェントがそれぞれ独立して似たようなヘルパースクリプトを書いたり、何かに対して同じマルチステップのアプローチを取ったりしていないか気づいてください。3つのテストケースすべてでサブエージェントが `create_docx.py` や `build_chart.py` を書く結果になった場合、それはスキルがそのスクリプトをバンドルすべきだという強いシグナルです。それを一度書き、`scripts/` に入れ、スキルにそれを使うように指示します。これにより、将来のすべての呼び出しで車輪の再発明をする手間が省けます。

このタスクは非常に重要であり（私たちはここで年間数十億ドルの経済的価値を生み出そうとしています！）、あなたの思考時間は妨げにはなりません；時間をかけて物事をじっくり熟考してください。修正案を書き、それを改めて見直して改善することをお勧めします。ユーザーの頭の中に入り込み、彼らが何を望み、何を必要としているのかを理解するために最善を尽くしてください。

### 反復ループ

スキルを改善した後：

1.  改善点をスキルに適用します
2.  ベースラインの実行を含め、すべてのテストケースを新しい `iteration-<N+1>/` ディレクトリで再実行します。新しいスキルを作成している場合、ベースラインは常に `without_skill`（スキルなし）です — これは反復間で同じままです。既存のスキルを改善している場合、何がベースラインとして適切か（ユーザーが最初に持ってきたオリジナルバージョンか、または前の反復か）あなたの判断を使用してください。
3.  `--previous-workspace` を前の反復に向けてレビューアを起動します
4.  ユーザーがレビューし、完了したと伝えるのを待ちます
5.  新しいフィードバックを読み、再度改善し、繰り返します

以下の状態になるまで続けます：
*   ユーザーが満足したと言う
*   フィードバックがすべて空になる（すべて良さそうに見える）
*   意味のある進歩が得られなくなる

## 高度なトピック: ブラインド比較

2つのバージョンのスキルをより厳密に比較したい状況（例：ユーザーが「新しいバージョンは本当に良くなっているの？」と尋ねる場合）のために、ブラインド比較システムがあります。詳細については `agents/comparator.md` と `agents/analyzer.md` を読んでください。基本的なアイデアは、どちらがどちらであるかを伝えずに独立したエージェントに2つの出力を与え、品質を判断させることです。その後、なぜ勝者が勝ったのかを分析します。

これはオプションであり、サブエージェントが必要で、ほとんどのユーザーは必要としません。通常は人間のレビューループで十分です。

## 説明（Description）の最適化

SKILL.mdフロントマターのdescriptionフィールドは、Claudeがスキルを呼び出すかどうかを決定する主要なメカニズムです。スキルを作成または改善した後、トリガーの精度を高めるために説明の最適化を提案してください。

### ステップ 1: トリガー評価クエリの生成

20個の評価クエリを作成します — トリガーすべきものと、トリガーすべきでないもののミックスです。JSONとして保存します：

```json
[
  {"query": "ユーザーのプロンプト", "should_trigger": true},
  {"query": "別のプロンプト", "should_trigger": false}
]
```

クエリは現実的で、Claude CodeやClaude.aiのユーザーが実際にタイプするようなものでなければなりません。抽象的な要求ではなく、具体的かつ詳細な要求です。例えば、ファイルパス、ユーザーの仕事や状況に関する個人的な背景、列名と値、会社名、URLなどです。少しの背景事情も含めます。小文字のもの、略語、タイプミス、またはカジュアルな話し言葉が含まれているものもあります。異なる長さのものを混ぜ合わせ、明確なケースよりもエッジケースに焦点を当てます（ユーザーはそれらを承認する機会を得ます）。

悪い例: `"データをフォーマットして"`, `"PDFからテキストを抽出して"`, `"チャートを作成して"`

良い例: `"今ボスからこのxlsxファイルが送られてきて（ダウンロードフォルダにあって、名前は 'Q4 sales final FINAL v2.xlsx' みたいな感じ）、利益率をパーセントで表示する列を追加してほしいそうです。収益はC列でコストはD列だったと思います"`

**トリガーすべき（should-trigger）** クエリ（8〜10個）については、カバレッジを考えてください。同じ意図の異なる言い回しが必要です — フォーマルなものとカジュアルなものなど。ユーザーがスキルやファイル形式を明示的に指定していないが、明らかにそれが必要なケースを含めます。あまり一般的でないユースケースや、このスキルが別のスキルと競合するが勝つべきケースも含めてください。

**トリガーすべきでない（should-not-trigger）** クエリ（8〜10個）で最も価値があるのは、ニアミス — スキルとキーワードや概念を共有しているが、実際には別のものを必要としているクエリです。隣接するドメイン、単純なキーワードマッチングではトリガーされるべきではない曖昧な言い回し、スキルが行うことには触れているが別のツールの方が適切なコンテキストのケースなどを考えてください。

避けるべき重要なこと: トリガーすべきでないクエリを明らかに無関係なものにしないでください。PDFスキルのネガティブテストとしての「フィボナッチ関数を書いて」は簡単すぎます — 何のテストにもなりません。ネガティブケースは本当にトリッキーなものにすべきです。

### ステップ 2: ユーザーとのレビュー

HTMLテンプレートを使用して、評価セットをユーザーに提示しレビューしてもらいます：

1.  `assets/eval_review.html` からテンプレートを読み込みます
2.  プレースホルダーを置き換えます：
    *   `__EVAL_DATA_PLACEHOLDER__` → 評価アイテムのJSON配列（引用符で囲まないでください — これはJS変数の代入です）。埋め込む前に、JSON文字列中の `<` を `<` に置換してください（例: `json.dumps(items).replace("<", "\\u003c")`）— クエリ文言に `</script>` が含まれていると、そのまま埋め込んだ場合にスクリプトタグが早期に閉じられ、ページが破損します。
    *   `__SKILL_NAME_PLACEHOLDER__` → スキルの名前
    *   `__SKILL_DESCRIPTION_PLACEHOLDER__` → スキルの現在の説明
3.  一時ファイル（例：`/tmp/eval_review_<skill-name>.html`）に書き込み、それを開きます：`open /tmp/eval_review_<skill-name>.html`
4.  ユーザーはクエリの編集、トリガーのオン/オフの切り替え、エントリの追加/削除を行い、その後「Export Eval Set」をクリックできます
5.  ファイルは `~/Downloads/eval_set.json` にダウンロードされます — 複数存在する場合（例：`eval_set (1).json`）に備えて、Downloadsフォルダ内の最新バージョンを確認してください。

このステップは重要です — 悪い評価クエリは悪い説明（description）につながります。

### ステップ 3: 最適化ループの実行

ユーザーに伝えます：「これには少し時間がかかります — バックグラウンドで最適化ループを実行し、定期的に確認します。」

評価セットをワークスペースに保存し、バックグラウンドで実行します（`aggregate_benchmark.py` と同様、skill-creator ディレクトリから実行してください — `scripts.*` の相対importがそこを起点に解決されるためです）：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

トリガーのテストがユーザーが実際に経験するものと一致するように、システムプロンプト（現在のセッションを動かしているもの）からのモデルIDを使用してください。

実行中は定期的に出力を監視（tail）し、現在どの反復にいるか、スコアがどうなっているかについてユーザーにアップデートを提供します。

これは完全な最適化ループを自動的に処理します。評価セットを60%のトレーニング用と40%のホールドアウトテスト用に分割し、現在の説明を評価し（信頼できるトリガー率を得るために各クエリを3回実行します）、失敗した内容に基づいて改善を提案するためにClaudeを呼び出します。トレインとテストの両方で各新しい説明を再評価し、最大5回反復します。完了すると、反復ごとの結果を示すHTMLレポートがブラウザで開き、過剰適合を避けるためにトレインスコアではなくテストスコアによって選択された `best_description` を含むJSONを返します。

### スキルのトリガーメカニズム

トリガーのメカニズムを理解することで、より良い評価クエリを設計するのに役立ちます。スキルは名前+説明と共にClaudeの `available_skills` リストに表示され、Claudeはその説明に基づいてスキルを参照するかどうかを決定します。知っておくべき重要なことは、Claudeは自身で簡単に処理できないタスクに対してのみスキルを参照するということです — 説明が完全に一致していても、「このPDFを読んで」のような単純な1ステップのクエリはスキルをトリガーしない可能性があります。これはClaudeが基本的なツールで直接処理できるためです。複雑な、マルチステップの、または専門的なクエリは、説明が一致したときに確実にスキルをトリガーします。

これは、評価クエリが、Claudeがスキルを参照することで実際に恩恵を受けるのに十分なほど実質的なものであるべきだということを意味します。「ファイルXを読んで」のような単純なクエリは、テストケースとして不適切です — 説明の質に関わらず、スキルはトリガーされません。

### ステップ 4: 結果の適用

JSON出力から `best_description` を取得し、スキルのSKILL.mdフロントマターを更新します。ユーザーに変更前/変更後を見せ、スコアを報告します。

### パッケージ化と提示（ファイル配信ツールが利用可能な場合のみ）

ユーザーにファイルを提示するツール — `present_files`、またはCoworkリモートの場合は `SendUserFile` — にアクセスできるかどうかを確認します。どちらもない場合は、このステップをスキップしてください。アクセスできる場合は、スキルをパッケージ化し、そのツールで結果の `.skill` ファイルをユーザーに送信します（他のスクリプトと同様、skill-creator ディレクトリから実行してください）：

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

提示された `.skill`（または単なる `SKILL.md`）のファイルカードには、ユーザーの組織がスキルの作成を許可している場合、**Save skill** ボタンが表示されます；それをクリックすると、スキルが彼らのプロファイルにインストールされます。

## Claude.ai 固有の指示

Claude.aiでもコアとなるワークフローは同じです（ドラフト → テスト → レビュー → 改善 → 繰り返し）が、Claude.aiにはサブエージェントがないため、いくつかのメカニズムが変わります。以下に適応方法を示します：

**テストケースの実行**: サブエージェントがないということは、並列実行がないということです。各テストケースについて、スキルのSKILL.mdを読み、その指示に従って自分自身でテストプロンプトを達成してください。一度に1つずつ行ってください。これは独立したサブエージェントほど厳密ではありませんが（あなたがスキルを書き、あなた自身がそれを実行するため、完全なコンテキストを持っているからです）、有用な健全性チェック（サニティーチェック）になります — そして人間のレビューステップがこれを補います。ベースラインの実行はスキップしてください — 単にスキルを使用して、要求された通りにタスクを完了させてください。

**結果のレビュー**: ブラウザを開けない場合（例：Claude.aiのVMにディスプレイがない、またはリモートサーバーにいる場合）は、ブラウザレビュアーを完全にスキップしてください。代わりに、会話内で直接結果を提示します。各テストケースについて、プロンプトと出力を表示します。出力がユーザーが見る必要のあるファイル（.docx や .xlsx など）である場合は、ファイルシステムに保存し、ユーザーがダウンロードして確認できるようにその場所を伝えます。インラインでフィードバックを求めます：「これはどうですか？ 何か変更したいところはありますか？」

**ベンチマーキング**: 定量的なベンチマーキングはスキップしてください — サブエージェントなしでは意味をなさないベースライン比較に依存しているためです。ユーザーからの定性的なフィードバックに集中してください。

**反復ループ**: 以前と同じです — 途中のブラウザレビュアーを省くだけで、スキルを改善し、テストケースを再実行し、フィードバックを求めます。ファイルシステムがあれば、結果を反復ディレクトリに整理することは可能です。

**説明の最適化**: このセクションでは `claude` CLIツール（具体的には `claude -p`）が必要ですが、これはClaude Codeでのみ利用可能です。Claude.aiの場合はスキップしてください。

**ブラインド比較**: サブエージェントが必要です。スキップしてください。

**パッケージ化**: `package_skill.py` スクリプトはPythonとファイルシステムがあればどこでも機能します。Claude.aiでは、それを実行し、ユーザーが結果の `.skill` ファイルをダウンロードできます。

**既存のスキルの更新**: ユーザーは新しいスキルを作成するのではなく、既存のスキルを更新するように求めているかもしれません。この場合:
*   **元の名前を保持する。** スキルのディレクトリ名と `name` フロントマターフィールドに注意してください -- 変更せずに使用します。例：インストールされているスキルが `research-helper` の場合、`research-helper.skill` を出力します（`research-helper-v2` ではありません）。
*   **編集前に書き込み可能な場所にコピーする。** インストールされたスキルのパスは読み取り専用の可能性があります。`/tmp/skill-name/` にコピーし、そこで編集し、コピーからパッケージ化します。
*   **手動でパッケージ化する場合は、まず `/tmp/` にステージングする**, その後出力ディレクトリにコピーします -- 権限の問題により直接の書き込みが失敗する可能性があります。

## Cowork 固有の指示

Coworkを使用している場合、知っておくべき主なことは以下の通りです：

*   サブエージェントを持っているため、メインのワークフロー（テストケースの並列スポーン、ベースラインの実行、採点など）はすべて機能します。（ただし、タイムアウトに関する深刻な問題が発生した場合は、テストプロンプトを並列ではなく直列で実行しても構いません。）
*   ブラウザやディスプレイがないため、評価ビューアを生成する際には、サーバーを起動する代わりに `--static <output_path>` を使用してスタンドアロンのHTMLファイルを書き出します。その後、ユーザーがクリックしてブラウザでHTMLを開けるようにリンクを提示します。
*   どういうわけか、CoworkのセットアップではClaudeがテスト実行後に評価ビューアを生成したがらない傾向があるため、繰り返しておきます：Coworkを使用しているかClaude Codeを使用しているかに関わらず、テストを実行した後は、自分自身でスキルを修正し訂正を試みる前に、人間が例を見るための評価ビューアを常に `generate_review.py` を使って生成すべきです（独自のブティックなhtmlコードを書かないでください）。あらかじめ謝っておきますが、ここからは大文字を使わせてもらいます：自分自身で入力を評価する*前に*評価ビューアを生成してください。できるだけ早く人間の前にそれらを出したいのです！
*   フィードバックの仕組みが異なります：実行中のサーバーがないため、ビューアの「Submit All Reviews」ボタンは `feedback.json` をファイルとしてダウンロードします。その後、そこから読み取ることができます（先にアクセスを要求する必要があるかもしれません）。
*   パッケージ化は機能します — `package_skill.py` はPythonとファイルシステムのみを必要とします。
*   説明の最適化（`run_loop.py` / `run_eval.py`）はブラウザではなくサブプロセス経由で `claude -p` を使用するため、Coworkでも問題なく機能するはずですが、スキルの作成が完全に終了し、ユーザーがそれを良い状態だと同意するまで保存しておいてください。
*   **既存のスキルの更新**: ユーザーは新しいスキルの作成ではなく、既存のスキルの更新を求めているかもしれません。上記の claude.ai セクションの更新ガイダンスに従ってください。
