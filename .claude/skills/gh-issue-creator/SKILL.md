# GitHub Issue Creator

ユーザーと会話しながらGitHub Issueの内容を詰め、`gh issue create` で実際に作成するスキル。

## 前提

- `gh` コマンドがインストール・認証済みであること(`gh auth status` で確認可能)
- 現在のディレクトリが対象の git リポジトリ内であること
- テンプレートは `.github/ISSUE_TEMPLATE/小タスク.md` と `.github/ISSUE_TEMPLATE/中長期タスク.md` を使う。リポジトリにこれらが存在しない場合は、テンプレートなしでシンプルなIssue(タイトル+概要程度)を作ってよいかユーザーに確認してから進める。

## 基本姿勢: 対話しながら決める

Issueの内容は、一度に全部を言い当てようとするより、要所要所で短く質問してユーザーから答えをもらいながら詰めていく方がいい結果になる。理由は単純で、「何を issue にしたいか」「何をもって完了とするか」はユーザーの頭の中にしかない情報で、コードやgit履歴を読んでも半分くらいしか推測できないから。憶測で埋めた内容を後からユーザーに直させるより、その場で聞いた方が早いし、出来上がるIssueの精度も上がる。

なので、以下のワークフローの「確認する」「尋ねる」は、迷ったときだけの例外処理ではなく、通常運転として扱う。ユーザーがすでに十分具体的に説明していて聞くことがなければ、その質問はスキップしてよい — 無理に埋めるための質問をする必要はない。

## ワークフロー

### 1. 何についてのissueか、まず聞く

- ユーザーの発言だけで内容(何を・なぜ)が十分明確なら、そのまま次に進んでよい。
- 「issue作って」「これissue化しといて」のように内容が薄い依頼なら、まず率直に聞く。「どんな内容のissueにしますか?」「不具合ですか、それとも新しい対応の話ですか?」など、会話として自然な形でよい。
- ユーザーの回答だけでは材料が足りない場合(例:「さっきの件」で詳細を思い出せていない)は、以下で直近の作業を補ってよい:
  ```bash
  git status --short
  git diff
  git log -5 --oneline
  ```
  ただし調べた内容を無断で採用せず、「〜という理解で合っていますか?」と一言確認してから次に進む。ユーザーが「それで合ってる」と言えば、細部の聞き直しは不要。

### 2. テンプレート種別を一緒に決める

- **小タスク**: すぐ手を動かし始められる粒度で、単一の変更や対応で完結するもの。
- **中長期タスク**: 複数の子タスク(小タスク)に分解されそうな規模で、目的や背景の説明が要るもの。

内容の規模感からどちらが良さそうか判断し、「小タスクとして作ろうと思いますが、それで大丈夫ですか?」のように、決定事項の通知ではなく提案として伝えて確認を取る。ユーザーが即座に「小タスクで」「これは大きい話だから中長期で」と自分で決めている場合は、そのままそれに従ってよい。

### 3. 親issueの候補を探す(小タスクの場合)

```bash
gh issue list --search "<内容に関連するキーワード>" --limit 10 --state all
```

関連しそうなissueが見つかったら、番号とタイトルを挙げて「これを親issueにしますか?」とユーザーに確認する。ユーザーがすでに親issue番号を伝えている場合は検索を省略してそれを使う。関連issueが見つからなければ「関連しそうなissueは見つかりませんでした、親issueなしで進めます」と一言伝えて次に進む。

### 4. 詳細を詰める

対象テンプレートを読み込み、見出し構成を変えずにプレースホルダ部分を埋めていく。埋める材料が会話やコード調査から十分に集まっているならまとめて書いてよいが、特に **close条件** はユーザーの意図がないと正確に書けないことが多いので、不明なら「何が終わったらこのissueをcloseできますか?」と聞く。

- **小タスク** (`親issue` / `概要` / `close条件`)
  - `親issue`: ステップ3で決まった番号(例: `#12`)、なければ空欄
  - `概要`: 何をするタスクか
  - `close条件`: 何が完了したらcloseできるか
- **中長期タスク** (`概要` / `目的` / `背景` / `close条件`)
  - `close条件`のデフォルトは「全ての子タスクが終了」。これで良いか、他に条件があるか確認する

タイトルは内容を要約した1行で作成する。ラベルはテンプレートのfrontmatter(`labels:`)にある値(`小タスク` または `中長期タスク`)をそのまま使う。

**close条件の書き方**: 可能なら「テストが通ればclose」「〇〇が実装されていればclose」のように、後から客観的に検証しやすい条件を優先して提案する。一方で「エミュレータで確認できたらclose」「スクショを貼ってclose」「レビューされればclose」のように、実装が終わった後にもう一手間の確認作業を要求する条件になる場合は、GitHubのタスクリスト記法(`- [ ] エミュレータで動作確認`のような形)で書くようユーザーに提案する。issueページ上でチェック状態が可視化され、実装完了後にその一手間が忘れられて放置されるのを防ぎやすくなる。

### 5. 最終確認してから作成する

生成したタイトルと本文をそのまま提示し、この内容で作成してよいか確認する。ここまでの対話で内容はすり合わせ済みのはずなので、この確認は形式的な最終チェックになることが多いが、それでも必ず一度提示してから作成する。ユーザーの確認なしに作成しない。

### 6. Issueを作成する

本文は一時ファイルに書き出し `--body-file` で渡す(改行やクォートの問題を避けるため):

```bash
gh issue create --title "<タイトル>" --body-file /tmp/issue_body.md --label "<ラベル>"
```

作成後、`gh issue create` が返すissue URLをそのままユーザーに提示する。

### 7. 作成後

issue URLを提示するだけでよい。ブラウザで開く必要があれば `gh issue view --web` を案内する程度に留め、勝手には開かない。

このissueを後でPRで解決する際は、PR本文に `close #<このissueの番号>` と明記するとマージ時にGitHubが自動でcloseする(`gh-pr-creator` スキル側の規約)ことをユーザーに一言伝えておくとよい。

## 注意事項

- Issue作成は他者にも見える(共有)アクション。ユーザーの確認なしに作成しない。
- close条件や概要は正直に、事実と意図に即して書く。憶測で断定的な記述をしない。
- 質問は一度にまとめて畳みかけず、会話の流れに沿って一つずつ聞く。ユーザーがすでに答えている情報を重ねて聞き直さない。
- 認証エラー(`gh auth status` が失敗)の場合は `gh auth login` を促す。
- `.github/ISSUE_TEMPLATE/` が存在しない、または対象テンプレートが見つからない場合は、テンプレートなしでの作成に切り替えてよいかユーザーに確認してから進める。
